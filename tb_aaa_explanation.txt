UNIVERSAL ARGUMENTS

Across all / most functions, the arguments: 
    x1: bottom left corner of village X value
        int x1 = loc_x - village_size / 2;
    z1: bottom left corner of village Z value
        int z1 = loc_z - village_size / 2;
    x2: top right corner of village X value
        int x2 = loc_x + village_size / 2;
    z2: top right corner of village Z value
        int z2 = loc_z + village_size / 2;
    
    These variables are used to keep spawned blocks, pathfinding 
        and waypoint checks within village bounds. 
        must be >= x1 && >= z2 && <= x2 && <= z2.

    path_map:  an array a C-style array of bool values.
                true if the block is NOT valid for paths/ waypoints
                false if the block is valid for paths/ waypoints
                to index this array:
                    path_map[ (reletive_x_value) * z_width + (reletive_z_value) ]
                where relative x/z values are is the coordinate within the village. 
                e.g.
                    origin is (0,0) and bottom right is (100,100) in a village size 100.
                

    surface_y:  The y-level of the ground. 

    cs_plots:   (C-style_plots) is an array of the Plots which is then iterated through.
                    Blocks taken by plots are avoided.
                    This had to be a C-style bc i wasnt allowed to use vectors. 
                    Its converted from the plots vector on main.

CLASSES: 

    Node, BfsQueue, waypoints, homemade

    


    Node            tb_bfs_node.h

    This class is used for BFS alg, 
        these nodes are the units used for pathfinding.

    Attributes:
        stores relative x/y values,
        
        stores parent node,
            This is so the found path can be backtracked
        
        stores the successor, 
            This is used by BfsQueue to upkeep the linked list. 

            

    Functions:
        None

        



    BfsQueue          tb_bfs_queue.h

    This class is used for the BFS alg,
        the queue is essentially a linked list.
        I think there is an existing library but wastn allowed to use it. 

    Attributes:
        stores the pointer to the head Node (headN),
            This is the node first in line -- next to be considered. 
        
        stores the pointer to the rear Node (rearN)
            This is the node last in line -- most recently added
        
        stores the length of the queue (size).
        
    Functions: 
        
        isEmpty()
            Returns a bool of whether the queue is empty.
                When the queue is empty, then there are no Nodes
                left to be considered.
        
        push(Node* newN) -- (newN --> new Node)
            Void function that adds a new Node to the back of the queue
        
        pop()
            Returns the Node at the front of the queue, 
                Then removes it. 
            It returns the first node because it is its turn to be considered
                It removes it as it no longer needs to be in line.





    waypoints       tb_waypoint.h

    This class is used to store details needed for the waypoints 
    
    Attributes:
        
        stores the x, z coordinates 
            which is where the waypoint exists at / will be built at
        
        stores the waypoint's children in a vector of plots ptrs
            This stores all of the plots which the waypoint needa connect to 
        
        stores whether it is linked
            This is used for the waypoint pairings later
            It ensures no circular paths are made and every waypoint
                becomes connect to a waypoint which can connect to all other waypoints;
                no isolated groups will be made
        
        stores the waypoint's distance from the centre (dist)
            This is used to connect waypoints closest together
                (like how it works with plots)
    
    Functions:

        print()
            Void function that prints the waypoint info in debug mode
                prints x,z coords, and the children





    Homemade        tb_homemade .cpp / .h
        
        Custom class that essentially works as a vector for coords

            and was scared to delete the files 
        
        It was used to keep track of path coords for avoidance, 
            which is why it is not used, as intersections are allowed
            if you wanna remove intersection you probs better off just using vectors

    bool* path_viability_check(int x1, int z1, int x2, int z2, const int surface_y);
        
        This function returns a bool array of all blocks within the village bounds
            true if the block is NOT valid for paths/ waypoints
            false if the block is valid for paths/ waypoints
        
        It checks if each block is (grass OR dirt) AND has air above it,
            meaning no obstacles obstruct the path.

        This C-style array becomes path_map.






    void bfs_path(  int x1, int z1, int x2, int z2, int xS,
                    int zS, int xT, int zT, Plot *cs_plots, int plot_amount,
                    bool* path_map, mcpp::BlockType block, const int surface_y)

        This function generates the path between two points.
            it features the BFS algorithm, block spawning 
            and removal of obstacle / plots from consideration.
        
        Arguments: 

            x1, z1, x2, z2 as described. 

            xS and zS are the coordinates which the path generation starts from.
                These are local coordinates.
                xS --> x Start && zS --> z Start
            
            xT and zT are the coordinates which the path generation is trying to reach. 
                These are local coordinates.
                xT --> x Target && zT --> z Target
            
            cs_plots is as described

            plot_amount is the length of cs_plots. 
                Used for iteration.

            path_map is as described. 

            block is just the block used to generate the path.
                pass any mcpp::Blocks::"..." as an argument. 

            surface_y is as described.
        
        Functionality: 

            Begins by iterating through all the plots, 
                marking occupied blocks as visited. 
                Visited blocks are unable to be considered in the alg. 
            This includes the two block buffer,
                but then undoes it for the two blocks infront of the door. 


            It then makes sure that blocks surrounding xS, zS, xT, zT are all unvisited. 
                This is to ensure that generation is possible. 
                This is mostly for definite insurance 
                    and was mostly from when path intersection was disallowed. 

            Standard BFS alg now begins, 
                expands in all directions from the Node first in the queue, 
                all neighbours valid for paths are then added to the back of the queue
                    (valid for paths if not visited && not an obstacle)
                This repeats until there are no valid Nodes or the target is found

            If a path is found, 
                it then runs from the target Node to its parent node,
                then to the parent's parent node, and on and on until it reaches the start of the path.
                All of these nodes are added to an array. 

                The created array of nodes is then iterated through in reverse to place blocks

                NOTE:   this seems in effective, the paths were stored in an array for 
                        path intersection avoidance. But since this was removed, the 
                        blocks can be placed while the Node's parents are iterated through,
                        without array storage. 

            Then all created objects are deleted.

    void quickSortPlots(Plot *cs_plots, int low, int high)

        This function is a quick sort algorithm 
            it sorts a C-style array of plots based on their proximity
            to the bottom left corner (the lowest x / z coords)
        This function can be replaced with any sorting method so long as it 
            reorganises cs_plots,
            or the code can be entirely refactored

        Arguments:

            low is the lowest index to be considered
            high is the highest index to be considered
                these have to be passed so that the recursivity works 
        
        Functionality: 
            Standard quicksort

            Makes sure the lowest index is lower than the highest
            
            Moves all Plots further than the last in the array to the end of the array

            It then repeats this process for all Plots on the left of the pivot 
                (closer to the corner than the pivot)

            It then repeats this process for all Plots on the right of the pivot
                (further from the corner)

            This is all repeated until the array is sorted

            Terrible explanation, but is a standard quicksort if you wanna use a more reliable source

    std::vector<Waypoint> group_plots(Plot *cs_plots, int plot_amount, int x1, int z1,
                                  int x2, int z2, const bool *path_map, 
                                  const int surface_y)

        Returns a vector of generated waypoint objects
            taking groups of 3 (to 5) consectutive plots from the plots array,
            the plots can be consectutive as they are sorted based on proximity
        For all of the waypoints generated, its houses it needs to connect to 
            is added to the children vector
        It then picks a location for the waypoints
            then moves it around until it finds a valid spot
        
        Arguments:
            cs_plots, plot_amount as described

            x1, z1, x2, z2 as described

            path_map, surface_y as described

        
        Functionality:
            Creates the empty vector of waypoints

            for each plot, it calculates its distance from the bottom left corner
                Then quick sorts them based on their distances,
                this means the vector of plots is ordered based approximately on how
                    close together they are

            Then calculates how many houses the waypoint needs to take as children,
                this is because the waypoints should have plots in groups of 3,
                    but this is not possible if the amount of plots is not divisble by 3,
                    8 plots should have a group of 3, and a group of 5
                    7 plots should have a group of 3, and a group of 4
                This amount of houses is then allocated to that waypoint
            
            For each waypoint, 
                the average x and z values of all the children is calculated
                Thus putting the waypoint in the centre of the group'

                Then the x and z is moved around until a valid location is reached

                Then the emeraled is placed

            Then return the vector of all waypoints created

            But I didnt do this to prevent path intersections in a way i could understand

        arguments: 
            x1, z1, x2, z2 are as described

            wp is the waypoint currently being connected to its children

            path_map, cs_plots, plot_amount, block is as described
        
            debug is a bool indicating whether the code is in debug mode

            surface_y is as described

        Functionality: 

            If the waypoint has children
                it loops through the vector of the waypoints children 

            The coordinate of the block infront of the door is then found, 
                as this is the coord the path is connecting to 

            Then the bfs path generation is ran

    void quickSortWaypoints(std::vector<Waypoint>& waypoints, int low, int high)
            
        Void function that is a quicksory algorithm,
            that orders the vector of waypoints 
            based on each waypoint's distance from the village centre
        
        To change this algorithm, it just must change the 
            waypoints vector that is passed by reference 
            Do so however youd like 

        Arguments:

            waypoints is a vector of waypoints passed by address,
                it is reorganised in place for consideration

            Low is the lowest index to begin the sort at

            high is the highest index to which the sort should go


                
        Functionality:

            Quicksort algorithm that works the exact same as the plot one
                (quickSortPlots())
            Except .dist is the distance of the waypoint to the centre





    void connectWaypoints(int x1, int z1, int x2, int z2, 
                        std::vector<Waypoint>& waypoints, bool* path_map, 
                        Plot* cs_plots, int plot_amount, mcpp::BlockType block, 
                        bool debug, const int surface_y) 
        
        Void function that spawns the paths between all of the waypoints,
            it pairs them up based on proximity,
            connecting one waypoint to the closest non connected waypoint

        Arguments:
            x1, z1, x2, z2 are as described

            waypoints is the vector of waypooints generated in group_plots(...)

            path_map, cs_plots, plot_amount, block is as described

            debug is the bool value indicating whether the code is running in debug mode

            surface_y is as described

        Functionality:

            Uses the quicksort to order the waypoints as described

            Iterates through all the waypoints to connect it 
                to the next closest one unlinked one

            The path is spawned between the two
            
            The waypoint currently iterated to is marked as linked, 
                but the waypoint which is found is not marked as linked
                this is so that multiple waypoints may connect to this waypoint
                    which would be rlly difficult to do if it was marked as linked

            This also means all waypoints connect to a waypoint which it is not currently linked to 
                preventing cycles from forming 

            



    void waypointPlatforms(const std::vector<Waypoint>& waypoints, 
                        const int surface_y) 
        
        Void function that spawns the waypoint structure at each waypoint
            minus the emerald block

        to change the structure, put wtv you want within the iterative loop 

        Arguments:

            waypoints, surface_y are as described

        Functionality:

            Loops through all of the waypoints in the vector 
                spwans the SPRUCE_WOOD_PLANK plank in the 8 neighbouring blocks
            
                Then spawns the REDSTONE_LAMP_ACTIVE and REDSTONE_BLOCK in the center,
                    the centre is the actual coordinate of the waypoint
            
                then moves on to the next waypoint

THINGS YOU MAY WANNA CHANGE 
    and how to do it




    OBSTACLE DETECTION

        Update path_viability_check(...) of (tb_bfs_alg.cpp) to set more indexes to true

        setting an index to true means this coordinate is not viable for a path to spawn on

        To add more obstacles
            set the index in the array to true when the new obstacle condition is met




        
    PATHFINDING ALGORITHM

        Update bfs_path(...) of (tb_bfs_alg.cpp) to spawn the blocks between
            (xS, xZ) to (xT, zT) in wtv way you want
            So long as the blocks are spawned 
        
        Can remove or add obstacle detection as wanted

        To add more avoidance systems, 
            I would reccomended setting the blocks of wtv you tryna avoid
            to be visited 




    PLOT GROUPINGS

        Simplest way would be to update or replace 
            quickSortPlots(...) of (tb_house_grouping.cpp) to reorder the cs_plots
            so that consectutive plot elements are right for being grouped together

            This keeps the grouping functionality which just groups plots neighbouring in the array

        
        OTHERWISE
            Update group_plots(...) of (tb_house_grouping.cpp) 
            to systemically create waypoint objects 
                and fill each created waypoint's children vector with the plots of the group

            This would take place on the loop found starting at line 196
            And line 185 (quickSortPlots(...)) would no longer be needed
    



    WAYPOINT RELOCATIONS

        Update waypointFits(...) of (tb_house_grouping.cpp),
            to change conditions which are considered
        
        AND 
        update group_plots(...) of (tb_house_grouping.cpp),
            from line 260 where the relocation code begins
            
            replace this with wtv such that 
                the waypoint's x attribute and z attribute
                gets finalised at a valid location




    WAYPOINT GROUPINGS
        
        Update connectWaypoints(...) of (tb_waypoint_gen)
            in such a way that bfs_path(...) is still called 
            to connect all waypoints to another waypoint

        This can be done by reordering the waypoints vector
            in such a way that consectutive waypoints can be ideal for joining
                this is how quickSortWaypoints(...) works
    




    WAYPOINT STRUCTURE

        update connectWaypoints(...) of (tb_waypoint_gen.cpp)
            in such a way that for every element of the vectors waypoints
            a structure is built

        CURRENTLY, 
            this is done using a loop that runs through all of the waypoints
            (line 102)
            Then building the structure
        
        NOTE:
            The emerald block is not spawned in this function, 
            that is done in group_plots(...) 
                line 360 of (tb_house_grouping.cpp)
